2) UPGRADE SYSTEM — WHAT IT WAS
================================================================================
UpgradeHandler was the economy-driven upgrade engine (withdraw money via Vault,
check island level, advance levels). It produced per-island upgrade levels for:
  UPGRADE_TEAM_LIMIT   = "team-limit"      -> max island members
  UPGRADE_WARP_LIMIT   = "warp-limit"      -> max warps per player
  UPGRADE_HOME_LIMIT   = "home-limit"      -> max homes per player
  UPGRADE_COOP_LIMIT   = "coop-limit"      -> max coop members
  UPGRADE_ISLAND_SIZE  = "island-size"     -> world border size (from level)
  UPGRADE_GENERATOR_RATES = "generator-rates" -> cobblestone generator loot table
  UPGRADE_BIOMES       = "biomes"          -> allowed biome list per level

Upgrade levels were persisted in DB table `island_upgrades`
  (island_uuid, upgrade_id, level), PK (island_uuid, upgrade_id).

CobblestoneGeneratorHandler consumed UPGRADE_GENERATOR_RATES and built a
weighted Material loot table (weighted random) used by CobblestoneGeneratorListener.

The Upgrade model (org.me.newsky.model.Upgrade) held
  (upgradeId, oldLevel, newLevel, requireIslandLevel, price).

================================================================================
3) LIMIT SYSTEM — WHAT IT WAS
================================================================================
LimitHandler tracked per-island block counts and entity limits (in-memory
ConcurrentHashMap<UUID, EnumMap<Material,Integer>>). It enforced:
  - block placement limits (config.getBlockLimit / limits.yml -> limit.blocks.*)
  - entity spawn limits (config.getEntityLimit / limit.entities.*)
  - recomputed on island load via calIslandBlockLimit()
  - tryIncrement / decrement on block place/break/burn (IslandLimitListener)
  - canSpawnEntity on creature spawn / transform (IslandLimitListener)
  - unload() on world unload (WorldUnloadListener)
